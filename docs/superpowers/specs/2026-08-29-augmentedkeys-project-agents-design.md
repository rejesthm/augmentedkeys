# AugmentedKeys Project Agents Design

**Date:** 2026-08-29
**Status:** Approved design; awaiting written-spec review
**Scope:** Project-scoped Codex agent configuration only

## Purpose

Create eight reusable, project-scoped Codex agents that improve development quality through explicit coordination, narrow specialization, isolated implementation, independent verification, and final review.

The agents must remain subordinate to owner-approved tasks and the existing AugmentedKeys operating constitution. They do not authorize product-core work, architecture decisions, dependencies, external actions, or automated development.

## Current State

- The repository has one `.codex/agents/verifier.toml` generated by the Loop initializer.
- That file uses the legacy `instructions` and `reasoning_effort` keys instead of the current `developer_instructions` and `model_reasoning_effort` schema.
- `.codex/config.toml` does not exist.
- `AGENTS.md` names future specialist roles but does not define reusable custom agents.
- `.loop/progress.md` correctly reports no active agents. Custom agent definitions describe available roles; they do not mean those agents are continuously running.

## Selected Approach

Use durable project-scoped custom agents under `.codex/agents/` and a project `.codex/config.toml` concurrency limit.

This was selected over:

1. Recreating temporary prompt-only roles for each task, which would be less consistent.
2. An automatic always-on agent pipeline, which would conflict with manual L1 Loop controls and consume unnecessary resources.

## Project Agent Defaults

`.codex/config.toml` will contain only project-agent settings needed by this design:

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

The limit applies to spawned specialists, excluding the primary agent. Three concurrent specialists plus the primary Conductor fit the current four-slot environment. Every custom agent defines its own model, reasoning effort, sandbox mode, and instructions, so no project-wide model default is needed.

## Agent Roster

| File | Agent name | Model | Reasoning | Sandbox | Responsibility |
| --- | --- | --- | --- | --- | --- |
| `conductor.toml` | `conductor` | `gpt-5.6-sol` | `high` | `workspace-write` | Coordinates an approved task, selects specialists, maintains task evidence, and enforces gates. It does not implement product code. |
| `researcher.toml` | `researcher` | `gpt-5.6-terra` | `high` | `read-only` | Gathers primary-source technical evidence, records access dates, separates facts from inference, and identifies licensing questions. |
| `flutter-builder.toml` | `flutter_builder` | `gpt-5.6-sol` | `high` | `workspace-write` | Implements approved Flutter application work through test-first, narrowly scoped changes and fresh verification. |
| `apple-specialist.toml` | `apple_specialist` | `gpt-5.6-terra` | `high` | `workspace-write` | Handles approved iOS/iPadOS research or implementation involving lifecycle, Core Audio, AUv3, and Apple-platform behavior. |
| `android-specialist.toml` | `android_specialist` | `gpt-5.6-terra` | `high` | `workspace-write` | Handles approved Android research or implementation involving lifecycle, AAudio/Oboe, device behavior, and Android compatibility. |
| `qa-performance-verifier.toml` | `qa_performance_verifier` | `gpt-5.6-sol` | `high` | `read-only` | Independently verifies requirements, tests, builds, device evidence, profiling evidence, and performance claims. |
| `licensing-security-reviewer.toml` | `licensing_security_reviewer` | `gpt-5.6-sol` | `high` | `read-only` | Reviews packages, assets, permissions, secrets, privacy, licenses, redistribution, and commercial-use evidence without making legal conclusions. |
| `final-code-reviewer.toml` | `final_code_reviewer` | `gpt-5.6-sol` | `xhigh` | `read-only` | Performs the final independent diff and repository review for correctness, regressions, safety, maintainability, and missing tests. |

Every agent file must use the current required fields:

```toml
name = "..."
description = "..."
developer_instructions = """
...
"""
```

Write-capable agents may additionally use local task commits only when the parent explicitly requests them. No specialist may push, merge, force-push, sign, release, deploy, schedule automation, change architecture, or expand its assigned scope.

## Approval and Delegation Boundary

Owner approval of one task authorizes the Conductor to select and launch the specialists necessary for that task without asking for separate approval for each agent.

That authorization does not cover:

- A different task or milestone.
- Product or architecture decisions.
- Dependency or asset adoption.
- Protected-path changes not included in the approved task.
- Credentials, accounts, hardware access, purchases, or legal conclusions.
- Destructive or external actions.
- Push, merge, signing, release, deployment, or automation unless separately authorized.

The Conductor stops and requests owner direction when any of those boundaries is reached.

## Loop Separation

The manual L1 project-health Loop remains report-only. Its existing conductor skill may update only `STATE.md`, `.loop/progress.md`, and `loop-run-log.md`, and it may not launch agents.

The reusable project Conductor operates only after an owner-approved development or research task exists outside the L1 Loop pass. The Loop may recommend one next task, but it cannot approve that task or start the agent team.

## Execution Workflow

1. The owner approves one bounded task.
2. The Conductor reads project memory, the task brief, applicable research controls, and the gate.
3. The Conductor chooses only the specialists needed for that task.
4. Up to three independent read-heavy specialists may work in parallel.
5. Research results return to the Conductor as evidence summaries rather than raw logs.
6. The Conductor resolves scope and sequencing before implementation.
7. One builder owns each sensitive file set. Independent writers use separate worktrees and may not edit the same sensitive files concurrently.
8. The QA/Performance Verifier checks the implemented result without editing it.
9. Findings return to the original builder for correction.
10. The Final Code Reviewer performs a fresh independent review after verification is clean.
11. The Conductor reports evidence, remaining limitations, and exactly one proposed next action.
12. Integration or publication occurs only with the required owner authorization.

## Agent Activity Ledger

`.loop/progress.md` records only currently running specialists under `# Active Agents`.

Example while a task is active:

```markdown
# Active Agents

- `apple_specialist` — researching Apple mobile audio constraints for the approved task.
- `android_specialist` — researching Android mobile audio constraints for the approved task.
- `licensing_security_reviewer` — checking dependency and redistribution risks for the approved task.
```

After the specialists finish, the section returns to:

```markdown
# Active Agents

None. No specialist agents are active.
```

Agent availability and agent activity are deliberately separate.

## Failure and Conflict Handling

- A failed schema or discovery check blocks commit and push.
- A failed test, build, gate, or verification returns to the assigned builder; it is not waived by another agent.
- Conflicting research conclusions remain separate until an evidence-backed synthesis or owner decision resolves them.
- Concurrent write conflicts stop the affected workstreams. The Conductor reassigns ownership or sequences the tasks.
- An agent that exceeds scope is stopped; its unapproved changes are not integrated.
- Licensing, security, credentials, hardware, destructive actions, and uncertain architecture escalate to the owner.
- No agent may lower a gate, increase the Loop budget, or convert a warning into a pass.

## Validation Design

Configuration validation follows a RED-GREEN sequence.

### RED

Run an acceptance check against the current repository and confirm it fails because:

- There is one agent file instead of eight.
- The existing file lacks `developer_instructions`.
- The existing file contains the obsolete `instructions` key.

### GREEN

After implementing the roster, verify:

- Exactly eight `.codex/agents/*.toml` files exist.
- Every agent has non-empty `name`, `description`, and `developer_instructions` fields.
- Agent names are unique and match the approved roster.
- Every model, reasoning effort, and sandbox mode matches this design.
- No obsolete `instructions` or `reasoning_effort` key remains.
- `.codex/config.toml` enables agents and limits concurrent specialists to three.
- The Loop conductor still prohibits launching agents during an L1 pass.
- `git diff --check` passes.
- `flutter analyze` passes.
- `flutter test` passes.
- An independent reviewer finds no Critical or Important issue.

## Acceptance Criteria

The change is complete when:

1. Exactly the eight approved agents are discoverable as project-scoped custom agents.
2. The legacy verifier is removed rather than becoming an unintended ninth agent.
3. Task-level delegation and owner-stop boundaries are explicit and consistent with `AGENTS.md`.
4. Read-only and write-capable roles match their responsibilities.
5. Concurrent specialist count is limited to three.
6. The manual L1 Loop remains report-only and unable to launch the team.
7. Configuration, Flutter analysis, Flutter tests, and independent review pass with fresh evidence.
8. The verified change is committed and pushed to `origin/main` without force.

## Explicit Non-Goals

- Running an agent task as part of this configuration change.
- Starting low-latency audio research.
- Implementing Flutter product features.
- Selecting audio, MIDI, plugin, persistence, or cloud architecture.
- Adding dependencies, assets, automation, Actions, releases, or deployment.
- Guaranteeing lower latency or higher product performance merely because agents exist.
