# Decision Evidence Protocol

This directory is the only canonical content root for the dedicated `governance/decision-evidence` branch. That branch is an append-only governance journal, not a product branch. Only the program controller may write it, only from a dedicated isolated worktree. Decision Steward and review sessions are read-only.

## Branch invariant

- Record one exact governance-base commit in the milestone ledger before branch creation. The first evidence commit is its direct child and adds immutable `docs/orchestration/decisions/governance-base.md` with that same exact SHA; every publisher invocation must prove this anchor and may not trust a later CLI base.
- Create `governance/decision-evidence` once from that base through `validate_decision_evidence.sh`; thereafter publish only fast-forward descendants with the guard's explicit refspec.
- The direct-child anchor is a `100644 blob`. After that anchor, every path changed by a new commit is a canonical `100644` Markdown blob under `docs/orchestration/decisions/m<digits>/{reviews,packages,verdicts,results,bindings}/`; a later corrected tip cannot sanitize an invalid historical mode or type. Reviews, packages, verdicts, and results are add-only; a binding may be added or updated to point at a later immutable sequence. Deletion is forbidden throughout history.
- Every commit after the governance base has exactly one parent. Never merge, rebase, force-push, rewrite, delete, merge product work, create or publish tags, sign, or use a direct raw push.
- Before consuming a decision, local and remote evidence tips must equal the exact current binding commit. Any later unconsumed commit or unequal tip requires `PAUSE_HUMAN`.

## Immutable review commits

Between complete package/verdict/binding or result/binding sequences, the controller may add one review at `docs/orchestration/decisions/m<digits>/reviews/<immutable-name>.md`. Each review commit is single-parent, add-only, changes exactly one canonical regular `100644` file, and records unique candidate, role, session, runtime, result, and finding-count fields. Complete review output is encoded as one canonical base64 line bounded by `--- BEGIN REVIEW OUTPUT ---` and `--- END REVIEW OUTPUT ---`. Metadata is parsed only before the begin marker and must include `Review output encoding: base64`, `Review output byte length`, and `Full review output SHA-256`; length and hash cover the exact decoded bytes without terminal-newline normalization. Metadata-looking or delimiter-looking decoded content neither satisfies a missing header nor creates duplicate metadata or escapes the frame. Reviews occur after candidate freeze, precede the consuming package, and are ancestors of that package. They are not ancestors of the candidate. Mutation, deletion, self-reference, candidate substitution, reuse after a candidate change, or an approval with nonzero blocking findings is invalid.

## Decision sequence

Every milestone acceptance, main integration approval, correction, human pause, or successor activation uses exactly three adjacent single-path commits. Each commit changes only the one path named for its stage; co-committed packages, verdicts, bindings, or other decision artifacts are invalid:

1. Immutable package: `docs/orchestration/decisions/<milestone>/packages/<action>-<sequence>.md`.
2. Verbatim read-only Steward verdict: `docs/orchestration/decisions/<milestone>/verdicts/<action>-<sequence>.md`.
3. Canonical current binding: `docs/orchestration/decisions/<milestone>/bindings/<action>.md`.

The package commit adds exactly one immutable package path. The verdict commit adds exactly one immutable verdict path. The binding commit adds or updates exactly one canonical binding path. An `APPROVAL` package records exact milestone, supported decision kind, contract path/commit, reviewed candidate, QA/Performance review, Licensing/Security review, Final review, target `main`, zero Critical/Important findings, limitations, and recovery instructions. Its action-specific bounds are mandatory: milestone acceptance names the completion package; main integration names `C`, `I`, the administrative delta, completion package, and current acceptance binding; next-milestone approval names the successor contract and entry-condition evidence. Package, verdict, and binding repeat the applicable bounds, and the publisher validates their identities and readable `100644` artifacts. An unsupported future approval kind cannot authorize. A `NEGATIVE` package records exact rejected evidence and counts, explicitly marks required evidence `MISSING`, or records `HUMAN_GATE` with a nonempty human-only reason plus all technically approving reviews. `HUMAN_GATE` preserves zero technical findings and supports only `PAUSE_HUMAN` with `DENIED` authorization. Every artifact has both a canonical path and exact readable commit, and every required field occurs exactly once.

The verdict records its evidence-package path and commit, exact verdict, milestone, contract, candidate, completion, target, successor, finding counts, decision, exclusions, `Controller recorder: program-controller`, `Steward role: decision_steward`, nonempty canonical Steward session, and calendar-valid UTC timestamp. Its disposition is `GRANTED` only for an approval compatible with an `APPROVAL` package; it is `DENIED` for `CORRECT` or `PAUSE_HUMAN` on a `NEGATIVE` package. The controller metadata surrounds but does not alter the Steward's verbatim verdict. The binding records `Binding status: Current`, exact package and verdict paths/commits, authorization disposition, resulting state, all decisive SHAs, and finding counts. Every referenced artifact is a canonical readable `100644` blob, never a directory or symlink. A later `CORRECT`, `PAUSE_HUMAN`, replacement approval, result, or binding supersedes the old binding; an old approval is never replayed.

## Acceptance and main-integration identities

The acceptance sequence binds frozen completion candidate `C`. Its current approval is then consumed by one exact five-path administrative transition: `ROADMAP.md`, `STATE.md`, `.loop/progress.md`, `docs/orchestration/milestones/M0_LEDGER.md`, and status fields in `docs/research/RESEARCH_INDEX.md`. It changes the milestone and every required `Verified` task to `Accepted`, replaces the prior ledger binding, records the accepted milestone tip `C`, and appends eleven calendar-valid dated rows, one for each R01–R10 transition and one for M0, with canonical `100644` modes and terminal newlines while preserving unrelated bytes. The resulting `I` is frozen before fresh reviews. The main-integration approval is recorded only on this evidence branch; no shared-state approval edit follows `I`. Its package and binding repeat `C`, `I`, the exact delta, current acceptance binding, fresh reviews for `I`, and unchanged target-main base. `C` and `I` remain distinct and may not be substituted.

Every guard invocation supplies a reviewed guard commit and expected SHA-256. The executable runtime bytes must match the canonical `100755` blob at that commit before evidence publication or main mutation is authorized.

## Main integration result

Every attempted integration is followed by an immutable result and a current result binding on this branch. The result records its unique status, consumed approval commit/path, authoritative guard command, complete guard output, pre/post local and remote `main` and evidence SHAs, environment, limitations, interruption point, recovery state, snapshot path, and replay disposition. Result metadata is parsed only before `--- BEGIN GUARD OUTPUT ---`; it requires `Guard output encoding: base64`, decoded byte length, and the SHA-256 of the exact decoded bytes. The body is one canonical base64 line, so control-looking or delimiter-looking decoded content remains opaque and terminal newlines are preserved exactly. The binding repeats the exact result commit/path/status, consumed approval, and replay disposition.

- `SUCCEEDED`: local and remote `main` are proved equal to the separately approved integration candidate `I`.
- `REJECTED`: the remote is proved unchanged at the recorded base and local `main`, index, and worktree are fully restored before refusal.
- `PARTIAL`: the result is ambiguous, externally moved, unverifiable, or not safely restored. It is non-replayable and requires `PAUSE_HUMAN`.

The controller publishes the result and binding through the evidence guard before updating the milestone ledger. Only `SUCCEEDED` may record integrated hashes. A prior approval cannot be retried after any bound result.

## Recovery

Main preflight requires a sterile worktree before reading contents: no tracked change, untracked or ignored path, empty directory, tab/newline name, symlink or symlink ancestor, directory in place of a regular file, FIFO, socket, or other special state. It has no credential-copy authority. The guard snapshots bounded metadata only into a validated private temporary directory: new, non-symlink, owned by the caller, mode `0700`, empty before capture, and under a standard private temporary root. It retains the actual directory and bytes whenever restoration or post-push state is unproved, including unexpected state created during merge. Such an attempt is `PARTIAL`, cannot replay its approval, and requires a current result binding plus `PAUSE_HUMAN`. Only proved success or exact restoration permits deletion of the known snapshot files and directory; arbitrary recursive deletion is forbidden.

On resume, inspect the ledger, the local and remote evidence tips, the branch-tip binding, and commits after the last consumed binding. Continue only when one ordered, current, unsuperseded sequence maps unambiguously from the recorded state to one permitted next state. A consumer must prove at the final evidence-binding tip that every prerequisite binding's latest change is still its recorded approval commit; checking only at an intermediate package commit is insufficient. Missing, conflicting, unreadable, internally inconsistent, or unverifiable evidence always requires `PAUSE_HUMAN` without mutation.
